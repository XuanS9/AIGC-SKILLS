# 项目资产总表与跨批次名称一致性

基础资产、场景与视频共用同一份项目资产总表；完整制作先统一规划、共享资产先定稿，再按场景分阶段交付。默认先锁定文字设定与空间布局再推进，无需回传全部实图；实图仅在明确要求或出现偏差时局部核对，用户明确要求快速预览时才联合交付预稿。所有资产、场景、视频、补镜、改写及分镜任务均执行本规范；样本与完整稿使用同一套名称。登记不等于生成，文字确认不等于视觉通过；建表不增加独立审批，已确认且未变内容直接复用。

## 生成前读取，交付时继承

1. 先读取用户项目目录已有的 `asset-registry.json`；用户指定的现有资产清单优先。已有清单为其他格式时，保留原始清单，按原名整理为可检查的 JSON，不重新命名。遇到两份清单冲突，先根据已确认交付记录核对；无法确定的条目标记待核对，不自行合并身份。
2. 没有总表时，从当前项目已确认的资产交付、实际文件及用户素材中建立总表。同一对象只登记一个基础调用名；继承旧项目已有名称，新建名称遵守根 SKILL.md 的资产命名规则（`@handle` = `@` + 纯中文名、不加类型前缀；类型前缀 `场景/角色/生物/道具` 只用于落盘文件名）。不从模板示例复制项目名称，不依赖模型记忆重新翻译。
3. 总表写入用户项目目录，不写入 skill 安装目录。无法访问项目目录时，在交付中附可保存的总表，并说明后续会话需要读取该表；不能声称已落盘或能跨会话自动记住。
4. 写基础资产、场景或视频提示词前都先查表，并核对当前阶段依赖。资产交付标题保留中文名称与调用名，场景图另按下节列图号、源图号及Clip；文件/待生成状态留总表和项目记录，不塞入复制用文件；视频的【参考素材职责】从总表提取本镜所需条目。样本阶段只写当前阶段样本，总表登记不提前展开整批或下游提示词。
5. 已登记调用名逐字复用（含每个汉字与限定词）；不得重译、缩写或给同一对象另起调用名。分段正文使用总表中的中文名称和必要可见特征；对白中的称呼可按剧情保留，但不能据此创建另一资产。
6. 文件更新保留 `handle`，更新 `file`、实际素材状态与对应视觉核对记录；新文件不能沿用旧版绑定/视觉通过，按真实进度退回状态，并在 `project.md` 标记受影响下游待复核。用户明确要求改名时，同步修改总表及项目内受影响的提示词；无法访问的旧交付列为待同步，不能声称全部修复。

## 文件格式

以下仅为格式示例，不是本项目已有素材，不得直接当作已生成或已绑定的资产：

```json
{
  "schema_version": 1,
  "assets": [
    {
      "name": "艾莉娅",
      "handle": "@艾莉娅",
      "file": null,
      "status": "planned"
    },
    {
      "name": "巨型森蚺",
      "handle": "@巨型森蚺",
      "file": null,
      "status": "planned"
    }
  ]
}
```

- `name`：稳定的中文显示名称。不同对象同名时加可辨识限定词，不把两个对象合并。
- `handle`：唯一逻辑调用名，为 `@` + 纯中文名（不加 `S/C/B/P` 或 `场景/角色/生物/道具` 等类型前缀）。同一总表不允许重复调用名；允许继承旧项目已有名称。`@Image1`、`@Video1`、`@Audio1` 等编号槽位为保留名称，不登记为项目调用名。
- `file`：实际文件路径或素材标识；尚未生成时为 `null`。相对文件路径以总表所在目录为基准。建议文件名如 `角色_艾莉娅_v01.png`（`类型_中文名_版本号`），不要把版本号或类型前缀写入逻辑调用名（`handle` 只用纯中文名）。
- `status`：`planned`（待生成/待补齐）、`available`（实际素材已具备）、`bound`（已绑定当前平台）、`verified`（绑定与引用效果已核验）。后三者必须有实际 `file`；只完成文字提示词时仍为 `planned`，不能升级状态。

总表可增加类型、身份特征、已知别名、基础资产、参考职责等说明字段，但 `name`、`handle`、`file`、`status` 必须保留，`schema_version` 保持 1。别名只用于识别旧称，不是新的合法调用名。状态衍生资产按根规范在后续需要时登记，并标明基础资产；不因建表批量制作衍生图。

### 制作确认与素材状态分开记录

- `status` 仅表示素材可用/绑定进度，不能代替提示词确认或视觉核对；即使是 `available`、`bound`，也不自动代表实图符合设计。`verified` 仍按上文表示绑定与引用效果已核验，不自动标记整个视频生成结果通过。
- 分阶段制作时按需记录 `prompt_review`；实际开展图片核对时再补 `visual_review`，不为每个资产强制建立视觉检查任务。旧表缺少这些可选字段时兼容读取，从实际证据补录；无证据不推断视觉通过，未核图不阻止文字定稿。
- `prompt_review` 记录提示词版本/项目相对路径、`pending` 或 `confirmed`、确认范围和依据；确认提示词后 `status` 仍可为 `planned`。
- `visual_review` 记录 `pending`、`passed` 或 `needs_revision`，`file` 指本次实际检查的文件版本，并记录检查依据与未解决差异。未出图时为 `pending`、`file: null`；`passed` 必须有实际图片检查证据且对应当前 `file`。文件换版重置为 `pending`，旧检查依据可存项目变更记录。
- 场景的 `layout.review` 记录文字设计确认，与 `visual_review` 的实图核对分开；`layout.basis` 写实际采用的依据。文字确认不代表外观/行动通道已在实图中通过。视频文字定稿前检查本镜所需设计与布局依赖，不要求先回传图片或全片资产齐备。
- 批次/阶段、交付模式、等待事项和依赖关系记在 `project.md`；不把阶段枚举混入 `status`，不把文字确认升级为 `verified`。当前 lint 检查原四个必填字段与引用，新增核对记录及实图证据由助手核对，不声称 lint 已验证视觉关卡。

可选核对记录示例（以下均为待核对，非实际检查结果）：

```json
{
  "prompt_review": {
    "version": "v01",
    "file": "prompts/basic-assets/角色_艾莉娅_v01.txt",
    "state": "pending",
    "scope": "角色基础组板",
    "evidence": null
  },
  "visual_review": {
    "state": "pending",
    "file": null,
    "evidence": null,
    "issues": []
  }
}
```

## 场景布局与批次复用

场景与相关视频任务完整读取 [文字空间布局](spatial-layout.md)。空间底稿放在现有 `S` 条目的 `layout` 中，不另建强制地图/计划文件；随场景样本确认，不新增审批。新写场景的相关字段应具备，简单场景仅填适用项；旧表兼容读取，缺项按已有确认设计补充，不伪造实图证据。资产表四个必填字段与 `schema_version: 1` 不变。

- `basis`：采用的文字设计版本/来源；采用已核对实图时写实际文件与依据，未读图不能写成实图提取。
- `version`、`review`：布局版本与「候选设计/文字布局已确认/待修订」。旧值「待出图核对」不等于默认阻塞；旧「已核对」须查依据区分文字还是视觉，不能自动升级视觉状态。
- `coordinates`：必要观察基准或相对空间关系；没有锁定构图时允许机位和画面方位按动作选择，不强填屏幕左右。已有项目坐标可继承，不杜撰东南西北；母图左右不当固定地理关系。
- `landmarks`：环境地标的稳定名称、数量、位置及连接，只含地形、建筑与固定空间结构。角色与道具不进入场景图；家具、货物、独立器械或固定的剧情物件均另记视频落位。
- `set_dressing`（兼容既有字段名）：仅记录固定环境结构和墙地表面磨耗、积雪等痕迹，不列角色或道具。
- `video_staging`（按需）：记录角色站位及家具、货物、器械、船只/载具、剧情物件的用途、落位和接触/固定关系，供对应视频提取；该字段不编入场景图片提示词。独立资产沿用其handle，一次性物件可在视频用文字说明，不因此强建资产。
- `paths`：每条连接的起点、经由区域、终点、通行宽度等必要条件；供视频提取路线，不自动把所有路线都写进每一镜。
- `height_relations`、`visibility`、`lighting`：适用的高差/尺度、母图关键连接可见性、相对地标的光向。`lighting`注明基准时段、天气及影视参考的曝光/光色依据，人物携带光源的移动与照明变化登记在对应视频片段。未定义区域先补设计，实际图中不可确认的内容与设计依据分别记录。
- 统一规划先协调动作需求与资产设定尺度，场景正文把位置/连接/高差写清；视频从同一版本提取机位、起点、路径、终点、朝向与高度。必要空间锚点要进入视频正文，总表不会传给模型，但不复制整段场景外观与布局。
- 生成图出现已知偏差时仅核对相关图片：妨碍关键动作则先修图，或经用户确认采用实际布局并同步场景提示词与相关视频。文件换版更新真实绑定/视觉状态；布局改变才修订设计版本，不因未回传所有图片而阻塞文字交付。
- 每阶段更新同一份总表，复用未变 handle 与布局。剧情破坏进入片段连续状态，基础布局保留；上游变更只复核受影响下游。名称 lint 不验证布局字段语义或图片几何，按空间规范做文本检查，视觉检查按需另报。

以下为已确认文字设计的结构示例，非已生成素材（可直接作为新场景条目模式）：

{
  "name": "瀑布木桥峡谷",
  "handle": "@瀑布木桥峡谷",
  "file": null,
  "status": "planned",
  "layout": {

  }

## 场景图编号与Clip双向映射

### 编号与来源

- 原剧本场号、视频 `Clip 批-序`、场景图 `image_id`、中文资产 `handle` 是四个不同层级；显式图片级@别名按下节单独登记。场景提示词以Clip作使用索引，原剧本场号保留 `source_scenes` 或项目对照，不放在主标题里混用。
- 母场景参考用 `S01、S02…`；同大场景内环境内容明显不同的图可用 `S01-01` 等稳定后缀。先按 [内容划分](spatial-layout.md#21-按环境内容划分参考图) 判断：同空间的角度、局部、反打和仅光照变化共用图，室内/门外雪院等不同内容分别生成。前缀不证明图生图关系，实际输入父级由 `source_image_id` 指定；独立生成可为null。
- 图号分配后保持稳定；同图文件更新只改文件版本，不改图号。新增图用未占用编号，删除或合并不迫使其他图重编号；旧项目已有编号优先继承，不擅自批量改名。
- 仅对独立图片检查 `image_id` 唯一。同空间不同镜头直接在Clip引用同一图，不默认建立一串备用视图。用户确定弃用/合并后，从当前 `view_plan`、场景正文、别名、图号列表和生成任务删除弃用条目，同步引用与计数；旧记录只留历史/归档，不留可选生成块。旧表 `reused` 记录兼容读取但不计新图，也不构成自指生成边。
- 真实源图可为根母图、同组已定衍生图，或共享入口/道路的关联场景图。每个独立图片的源图必须存在、不是自己，整条依赖链无环；未有实际文件时照实记null，不用编号伪造输入图。

### 写回现有总表

沿用 `schema_version: 1` 与资产四个必填字段，不新建第二份索引文件。下列字段仅在任务使用场景图片时补录；旧表可根据现有交付补齐，不推断历史出图或绑定已完成。

- `assets[S].view_plan[]`：记录 `name`、`image_id`、`source_image_id`（无来源为null）、`generate_separate_image`、`generation_method`（如母图/`image_to_image`/复用）、`actual_file`、`prompt_section`、`clip_scope`。可保留更详细的 `source_view`，其资产/视图与 `source_image_id` 必须指向同一张图。
- `video_delivery.clips[].scene_image_references[]`：每条记录 `image_id`、用途 `role`、`time_range_seconds`（片内起止；不限制时段为null）、`actual_file` 与 `platform_slot`。一个Clip需要多个图片时逐项列出，不只写一个模糊的母场景名。
- 同一图片在一个Clip内多次回切时，每个连续使用区间登记一条相同image_id的引用，`time_range_seconds`仍是单个起止对；相同图号复用不新增图片。标题按图合并列明各区间，不能用包含空档的大区间冒充连续取景。
- 从上述Clip引用反向生成场景标题的适用Clip，保证场景→Clip与Clip→场景一致。若标时间，范围必须在对应Clip内且与实际演出一致；资源可以同时参考，不机械要求所有图的时间范围互斥，也不擅自按资源列表重剪镜头。
- `image_id` 只作选图和绑定索引，不替代 `@中文场景名` 或 `@Image1` 等当前真实平台槽位。绑定时应逐一对齐“图号→实际文件版本→本次上传槽位”；同一母场景的不同图不能只绑定一个名称后任意混用。
- 未生成的图片 `actual_file: null`；只写完提示词时资产 `status` 仍为 `planned`。提示词确认、源图可用性、视觉检查与绑定分别记录；图号合法不等于可提交生成。
- 保存图片可带图号，如 `场景_S01-01_长屋_门外雪院_v01.png`；仍保留中文场景/视图名与版本，不擅自重命名已交文件，不另建计划文件名字段。

### 干净标题与校验边界

常用文件按 `SKILL.md` 示例，只保留图号/场景视图名/源图/Clip或视频时长及独立复制块；源剧本对照、版本、确认状态、备注与检查记录放现有项目文件。正文中的源图描述是图生图操作内容，不应因去备注而删掉。

每次交付、改号、合并视图或换源图后，核对独立图唯一、复用归属、源图存在且无环、Clip存在、时间范围合法、两个文件标题与总表双向对应。未知源图/Clip、重复独立图号和冲突时段需先修复，不能宣称可绑定。

现有 `seedance_lint.py` 仅核对中文调用名与相关模型规则，`director_contract_lint.py` 仅核对四段式、时间轴与对白；两者都不自动证明本节S图号、源图链或双向映射正确。这些由助手另作数据与文本核对，实际图像内容和平台绑定继续单独验收。

## 显式场景图片引用别名

视频采用直接 `@角色名` / `@道具名`，而不是再重复基础外观。需要按具体场景图直接@时，可在同一总表显式登记图片级作者用别名；这是已有S图号的附加引用层，不改变 `assets[].handle` 的中文命名，也不是新增场景资产。

下列字段追加到上面的总表（不是独立总表）：

```json
{
  "reference_aliases": [
    {"handle": "@S01", "image_id": "S01", "asset_handle": "@长屋", "file": null, "status": "planned"},
    {"handle": "@S01-01", "image_id": "S01-01", "asset_handle": "@长屋", "file": null, "status": "planned"}
  ]
}
```

- 仅用户要求按图号直接@或实际平台采用这种自定义名时使用，不能根据S图号自动推定已经有素材或上传槽位。未声明的 `@S01` 仍按未知引用处理。
- 每个别名必须对应一个已有S资产下、同image_id的独立view_plan条目；复用记录不再声明另一别名。别名file须与该视图actual_file一致，available/bound/verified必须有实际文件标识，不能继承母场景的状态冒充该视图可用。
- 用户指定直接引用的文字母稿可先登记planned/null，交付状态如实留项目记录；执行时仍需实际图并核对平台绑定。@S作者别名不等于@Image1等真实上传编号，必要时按本次实际附件映射替换。
- `seedance_lint.py --asset-registry` 已支持此可选字段：检查显式别名、独立视图、冲突、file/status；planned引用给警告。它仍不检查图片内容、真实上传结果、源图链或完整Clip双向映射。
- 不因资产直接引用而删掉动作、空间锚点、持物状态或剧情要求的可读窗口。例：令状图负责其字样设计，视频写“正面清楚可读、手指按住被风掀起的纸角”，不必再复制整个道具定义。

## 视频缺项与平台绑定

- 视频需要而总表没有的关键资产，先查是否为已有对象的别名。确认是新对象才登记 `planned` 并注明待补齐；完整制作返回本场景相应基础资产/场景阶段补齐，不连带重做已确认内容。仅视频请求只登记缺项，保持请求范围。
- 默认未回传实图不阻止文字交付；设定与布局已确认、文本检查通过即可文字定稿，块外说明实图未核对及素材/绑定状态。关键设计未定、未知参考内容影响执行或已知冲突未解决时，仅受影响部分为条件性预稿。实际提交提示词仅用真实可用标签；默认未生成/未绑定的逻辑调用名留在规划清单，正文用稳定中文名称描述。用户明确要求直接@母稿时，可使用已登记的planned逻辑引用，但须在块外标明待生成/待绑定，不称可提交；两条路径都不能伪装成已上传素材。模式必需素材或当前绑定未齐全时不称可提交；用户明确选择纯文字生成且模式支持时按该路径核验，不强制无关资产阶段。
- 项目逻辑调用名与平台槽位分开维护。在每个生成片段的交接清单记录「调用名 → 实际文件 → 当前真实标签/槽位」，例如已实际绑定后的 `@艾莉娅 → 角色_艾莉娅_v01.png → @Image1`。槽位可随单次上传顺序改变，不据此修改总表中的调用名，不把上一片段的槽位直接沿用到下一片段。
- 平台支持自定义 Elements 名称时沿用总表调用名，并核对实际附件；只支持编号时使用真实编号。音频、视频及站位参考也可登记在总表中，沿用其已有名称及实际参考职责。

## 交付前核对

每次样本和完整交付都检查：

1. 使用的是当前项目总表，资产标题、视频锁定栏和正文是否指向同一对象。
2. 每个资产调用名是否在表中且逐字一致；不能在视频里另行声明一个新名称来绕过检查。
3. 同一对象是否被换名、重译或重复登记；正文中文名称与身份特征是否一致。
4. 新需求、未生成素材、待绑定项是否明确标记；状态不能靠文字推测。
5. 每个片段的真实平台槽位是否对应正确文件，是否把状态衍生图误当基础资产。
6. 场景图号、直接源图号与Clip双向映射是否一致；复用图是否被误当成新图，图号是否被误当成上传槽位；见上节专门核对范围。

对含资产调用名的提示词，从 skill 根目录运行：

```bash
python3 scripts/seedance_lint.py --preflight --file /path/to/prompt.txt --asset-registry /path/to/project/asset-registry.json
```

检查器对照总表检查未登记调用名、大小写漂移、重复名称及调用名、表结构和待补齐素材；未知调用名即使在提示词内部声明过也会失败。`planned` 引用给出警告，不阻断文字方案评审。未传总表时，报告明确提示未做跨批次核对。

`@Image1`、`@Video1`、`@Audio1`（含空格编号形式）是平台槽位，不作为项目调用名检查；它们的实际绑定按每片段交接清单核对。脚本不验证文件是否上传、不核验视觉效果，也不能可靠识别无 `@` 的正文换称或两个不同名称实为同一对象，必须结合以上人工语义核对。检查通过不等于素材已可提交生成。
