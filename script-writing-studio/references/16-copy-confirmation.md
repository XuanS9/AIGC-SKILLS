# 文案交付、来稿再创作与确认

> 3–30分钟完整作品按 `19-runtime-structure.md` 确认具体单片/单集目标、全片覆盖与长内容接续；局部任务只处理相关范围，不强制跑其他Skill。

本文件只定义文案职责。先执行 `00-preflight.md`；制作与画布任务分别路由到相应Skill，不在此读取其操作模块。

## 1. 任务范围

- 完整视频创作/完整改稿仍先交独立叙事文案，供用户明确确认。粘贴完整稿、助手自称定稿、没有提出异议或只说“继续”都不自动构成确认。
- 单阶段优先：只要创意、会诊、台词、纯影视稿或一个开场，就交该范围；不强行展开全片。
- 维护Skill、仅供参考的案例不是作品生产授权；只诊断时不擅自改稿。
- 说明/动作用简体中文，对白默认英文，用户指定覆盖。这里的文案不是自动改成口播、梗概或台词清单。

## 2. 来稿再创作：原稿不等于锁定稿

用户交现成剧本用于创作时，默认授权实质性再创作：核事实和明确保留项，文案会诊，正文写作重构叙事并由对白精修重写/增补对白，交付更好的完整文案；不能把改稿建议代替改后正文，也不逐句请求改写许可。

- 可重写开场、场次拆并与呈现顺序、冲突推进、角色策略、对白和必要反应。保留有用优点，不以改动数量证明优化。
- 提升质量不等于增加字数。新内容须推进事件、关系、信息或选择；可删重复，可保留成立的沉默，不让所有人说金句，不为加戏超过片长。
- 事实、真实事件因果、数字单位、政策/专业条件不能透支。可改变叙述顺序，不能偷换事实发生顺序；时间压缩不能暗示虚假因果。
- 用户明确锁定的台词/关系/结局保持；改变题材、核心关系、价值方向或结局先确认。
- 核事实不护错误：稿件不是证据，查出明确错误说明并纠正；和锁定内容冲突时指出，不默改也不照搬。证据不足标待核，不虚构重大事故、恶行、技术突破或真实人物动机。
- 虚构对白可改，真实人物的戏剧化对白须与事实相容且说明非史料原话；直接引语须准确引用。改成意译/戏剧化表达后取消原话标识，不把改写署成名言；改编声明不能豁免事实错误。
- 明确确认并要求原样制作的稿件、只诊断、仅参考和维护案例不触发默认再创作。不冒称用户已确认。

## 3. 修改前的梗概确认闸门

凡是对已有剧本进行剧情修改、重写、重排场序、调整人物选择、改变冲突推进、增删关键事件或改写结局，必须先交一份更新后的“剧本梗概表”给用户审核。梗概表应明确标出本次修改涉及的旧版→新版变化，并至少说明故事承诺、主角目标与代价、主要阻力、关键事件链、信息/伏笔、人物选择及后果、情绪路线、结尾状态、全片预计时长、各主要段落的大概时长、开场承诺和首个有效变化的预计出现时间，以及制作影响。梗概表中的时长采用“预计/约”，用于检查开场是否过长、信息是否重复和是否存在无变化停留，不等于平台数据或观众实测。

在用户明确审核通过梗概表之前：
- 不写完整修改后剧本；
- 不以片段、场景正文、完整对白或“先写出来再看”为替代；
- 不把助手自检、用户未回复、用户说“继续”或仅同意某个局部建议视为梗概确认；
- 如用户只确认部分范围，只能修改已确认范围，受影响的其他剧情继续等待确认。

用户审核通过梗概表后，才按确认骨架写完整剧本，并在交稿时标明新的 `copyVersion`、确认范围、保留项、变更项及待确认状态。若完整剧本写作过程中发现必须改变已确认骨架，应暂停正文，重新提交受影响的梗概表，不得在正文中悄悄改方向。

## 4. 独立完整交稿

标题、预计时长、场次/地点/时间、人物、可见动作、完整对白/旁白和必要声音/转场；附精简事实/改编说明、待核项及真正影响制作的风险。按 `15-dramatic-tension.md` 核开场、因果、对抗和回报，改开场同步检查后续动机与结尾。

按实际语言估时，动作/对白可重叠的时间不重复计算；自然语速和必要停顿不能为满足片长而忽略。产出copyVersion与待确认范围，不仅交建议，也不提前附模型提示词、资产或逐镜生产表。

## 5. 确认的是哪一版

- 用户对具体稿件明确表示“文案确认”“就按这一稿制作”或同等意思才解除文案门槛；指代不清先问具体版本，不猜。
- 已明确确认的版本直接继承，不再索要形式确认。只确认某场只解锁该范围；若只记录确认、暂不制作，则尊重暂停。
- 下游唯一来源是用户确认稿，不是用户最初粘贴的底稿或助手内部自检版，除非用户确认的就是原稿。
- 剧情、对白、事实或结局进一步改动，新版回到待确认。用户精确指定替换并明确按此制作，可作为对该确定改动的确认；开放式“更有力一点”仍需回交稿件。
- 事实错误不能因已确认而照用：说明修法，停受影响部分，改后再确认。未受影响内容保留。
- 只调整下游执行格式且不改文案，不需要重新确认整篇。文案确认不等于事实核验通过、素材验收、工具审批或生成授权。

## 6. 文案交接

交给脚本包Skill：`项目｜copyVersion｜确认范围与证据｜唯一正文/定位｜语言/片长｜锁定内容｜事实/改编/风险｜关键选择、反应及情绪回报`。

只有文案确认过关才路由制作；具体制作条件由脚本包Skill负责询问。草稿同步交画布Skill且仅限文案与管理状态；新稿待确认期间不覆盖旧确认版生产输入。完整文案交付不宣称整包完成。

## 7. 制作交接的唯一来源与完整性闸门

脚本包不是重新理解故事，而是把**已确认的文案输出转换成制作表达**。交接时必须同时提供以下五层信息：

1. **唯一正文**：确认版 `copyVersion`、完整正文或明确的场次范围；脚本包不得以梗概、大纲、助手记忆或最初来稿替代。
2. **逐场定位**：场号、地点、时间、出场人物、场景顺序、预计片长，以及局部任务的起止边界。
3. **叙事锚点**：每场的人物当下目标、阻力、关键选择、信息释放、关系变化、必须看见/听见的证据、段末状态。
4. **语言与表演锚点**：逐字对白/旁白、说话人、画内/画外或旁白属性、语气/潜台词中已锁定的部分；没有锁定的表演不伪装成定稿事实。
5. **变更与风险**：锁定内容、事实/改编说明、待核项、不得改动项，以及允许制作层自行决定的范围。

交接前做一次**文案—交接单一致性检查**：正文场次、人物、对白、道具、时间线、结尾状态与上述摘要逐项对应。摘要不能新增正文没有的剧情，也不能省略会影响制作决策的选择、反应、证据或末态。发现缺失时优先补齐交接信息；若缺失来自正文自身，则返回文案阶段，不让脚本包猜测。
